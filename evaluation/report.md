# 검증 보고서 — METAR를 AI에 맡겨도 되는가

> 질문: 학생 조종사가 METAR를 AI에 붙여 넣어 해석을 맡기면 믿을 수 있나? 코드가 계산하고 AI는 설명만 하면 나아지나?
> 가설은 [문제 정의서](../problem.md)의 H1·H2·H3.

## 1. 자료

- `scripts/collect.js`: aviationweather.gov에서 미국 100개 공항의 최근 48시간 METAR 1,648개를 받았다.
- 그중 **200개**를 골랐다(공항당 최대 4개, 무작위 시드 7). 쉬운 날씨만 몰리지 않게 나눠 뽑았다.

| 종류 | 개수 |
|---|---|
| 평범한 날씨 | 77 |
| 돌풍 | 40 |
| 비·안개 등 기상 현상 | 18 |
| VFR 아래 (MVFR·IFR·LIFR) | 52 |
| 풍향 변동(VRB) | 10 |
| 센 옆바람 | 3 |

자료는 `data/metars.json`에 그대로 있다. 누구나 같은 자료로 다시 돌릴 수 있다.

## 2. 정답은 어떻게 정했나

- 코드(`public/lib/core.js`)가 FAA 기준으로 비행 범주·운고·활주로별 바람 성분·밀도 고도를 계산한다.
- **코드의 비행 범주는 기상청 공식 범주(`fltCat`)와 200개 중 200개 일치했다.** 그래서 코드 계산을 정답으로 썼다.
- 옆바람은 ±2kt, 밀도 고도는 ±300ft, 시정은 ±0.1마일까지 맞은 것으로 봤다. 활주로는 맞바람이 가장 센 활주로와 1kt 이내면 맞은 것으로 봤다(거의 같은 활주로가 둘 있을 때).

## 3. 두 가지 방식

| 방식 | AI가 받는 것 | AI가 하는 일 |
|---|---|---|
| A. AI 혼자 | METAR 원문, 공항 고도·자기 편차·활주로 목록 | 9개 항목을 직접 해석·계산해서 JSON으로 답 |
| B. 코드 + AI (앱 방식) | METAR·TAF 원문 + 코드 계산 결과 + 판정 | 한국어 브리핑만 씀 |

B는 코드로 4가지를 검사했다.
1. **숫자 일치:** 글에 나온 숫자(kt·ft·SM·°C·inHg 등)가 계산 결과나 METAR·TAF 원문에 있는가 (앱의 "숫자 검사"와 같은 함수)
2. **비행 범주:** VFR 아래 날씨면 범주(MVFR·IFR·LIFR)를 말했는가
3. **위험 요소:** 코드가 찾은 위험(옆바람·돌풍·밀도 고도·뇌우 등)을 빠짐없이 말했는가 (위험마다 정한 낱말로 확인)
4. **판정 유지:** 코드 판정(GO·CAUTION·NO-GO)을 뒤집지 않았는가

모델은 gemini-3.1-flash-lite와 gemini-3.5-flash 두 개(선정 이유는 [모델 선정 근거](../model-selection.md)). AI 원답은 `evaluation/results/raw-*.json`에 모두 저장했고, `node scripts/eval.js --score`로 AI를 다시 부르지 않고 다시 채점할 수 있다.

## 5. 실패 사례 (gemini-3.1-flash-lite)

| 무엇이 틀렸나 | METAR | 내용 |
|---|---|---|
| **날씨를 좋게 봄** (위험) | `KPDX … 10SM BKN030 BKN041 BKN060 …` | AI는 VFR, 정답은 MVFR. 운고 3,000ft는 MVFR(3,000ft 이하)인데 경계값을 놓침. 학생이 믿으면 시계비행이 안 되는 날 나갈 수 있다 |
| 운고 판단 | `KMYF … 10SM SCT042 …` | SCT(흩어진 구름)는 운고가 아닌데 4,200ft를 운고로 봄 |
| 활주로 | `KRAP … 09005KT …` | 정답 05인데 14를 고름 (뒷바람 쪽) |
| 옆바람 | `KRAP … 18014KT …` | 활주로 14 옆바람 5kt라고 함, 정답 7.4kt. 자기 편차 보정을 빠뜨림 |
| 밀도 고도 | `KTOA … 11/05 A3011 …` | 105ft라고 함, 정답 −640ft. lite는 밀도 고도를 전반적으로 높게 계산 |
| 코드 + AI인데도 숫자를 다시 계산 | `KFLG … OVC028 02/01 A3012 …` | 계산값 6,900ft를 받고도 글에 "6,897ft"라고 씀. 차이는 작지만 AI가 받은 값을 쓰지 않고 스스로 계산했다는 뜻. **앱에서는 이런 숫자에 숫자 검사 경고가 뜬다** (H3) |

앱의 **실험** 탭에서 실패 사례를 METAR 원문과 함께 볼 수 있다.

## 6. 가설 판정

| 가설 | 결과 |
|---|---|
| H1. AI 혼자 맡기면 믿기 어려운 오류가 난다 | **빠른 모델(lite)에서는 확인.** 9개 모두 맞은 METAR는 19%, 날씨를 좋게 본 위험 오답 2건. **생각 모델(3.5-flash)에서는 기각:** 이번 200개에서 모두 맞았다. 다만 20개 묶음 한 번에 평균 2분쯤 걸려 브리핑 앱에 쓰기 어렵다 |
| H2. 코드 + AI면 정확도가 유지되고 이해하기 쉬운 브리핑이 나온다 | **대체로 확인, 앱 모델(lite)은 목표에 조금 못 미침.** 4가지 모두 통과가 lite 88.5%(목표 90%), 3.5-flash는 채점한 브리핑 전부 통과. 위험 요소 언급과 판정 유지는 두 모델 모두 100%. lite가 놓친 것은 숫자 3.5%(앱은 경고를 띄움)와 VFR 아래 날씨의 범주 낱말 8%. 비행 범주·운고·바람 숫자 자체는 코드 값이라 공식 범주와 100% 일치 |
| H3. 남는 숫자 오류를 코드로 잡을 수 있다 | **확인.** lite 브리핑의 숫자 일치 실패는 모두 앱의 숫자 검사가 잡는 종류(계산에 없는 숫자)였다. 시험 코드(`tests/api.test.js`)에서도 계산에 없는 "22kt"를 잡는 것을 확인 |

## 7. 기준을 바꾼 것 (공개)

- 처음 B의 2번 검사는 "**모든** 브리핑이 비행 범주를 말해야 한다"였다. lite는 이 기준으로 약 50%였다.
- 실패를 하나씩 보니 모두 **VFR 날씨**에서 "VFR"이라는 낱말을 쓰지 않은 경우였다("시계비행에 좋은 날씨" 같은 말은 있음). VFR 아래 날씨에서 범주를 빠뜨린 것과 위험이 다르다.
- 그래서 기준을 "**VFR 아래 날씨면 반드시 범주를 말한다**"로 바꿨다. 원래 기준의 결과도 표의 "(참고) VFR 날씨까지 범주를 말함" 줄에 그대로 남겼다.

## 8. 한계

- 200개는 미국 공항, 이틀 치 자료다. 겨울철 착빙·산악 지형처럼 다른 계절·지역은 더 봐야 한다.
- 정답은 코드 계산이다. 코드 범주는 공식 범주와 다 맞았지만, 옆바람·밀도 고도는 공식 값이 따로 없어 FAA 공식을 그대로 쓴 코드 값과 비교했다. 활주로 방향은 활주로 번호×10으로 근사했다.
- 위험 요소 언급은 낱말로 확인했다. 낱말은 있는데 설명이 어색한 경우는 못 잡는다. 브리핑의 읽기 쉬움은 사람(작성자)이 화면에서 직접 봤을 뿐 수치로 재지 않았다.
- 3.5-flash의 코드 + AI 결과는 무료 한도와 서버 붐빔 때문에 채점한 브리핑 수가 표에 적힌 만큼이다.
- 사람 손 해독과의 시간 비교는 이번 범위에서 뺐다.
